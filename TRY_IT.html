Your first comparison, then your next build

Free pre-release 0.3.3 · No automatic upload · Use only firmware you are allowed to process.

  1. Install from the editor. In VS Code Extensions, search fwmemguard.fw-mem-guard and install the pre-release. Open a folder you control and trust. Marketplace listing.
  2. Check the bundled demo. Run FW Mem Guard: Run Demo from the Command Palette. BUDGET_EXCEEDED is intentional: Flash +51,200 B and RAM +27,136 B exceed the demo growth limits.
  3. Try the verified real-firmware pair. Follow MicroPython v1.24.1 / NUCLEO_F411RE. Keep the four original firmware files unchanged. Select FLASH (not FLASH_TEXT) and RAM. Use Flash total 524288, growth 8240; RAM total 114688, growth 4096 bytes. Expect PASS. Edit RAM growth to 4095: expect exactly one violation, actual=4096 and limit=4095. Restore 4096: expect PASS.
  4. Configure your two completed builds. Run Set Up / Update Project. Choose baseline MAP + matching ELF, then current MAP + matching ELF. Preserve a fixed baseline at separate paths. Confirm Flash/RAM coverage and enter all four budgets. Zero growth means no positive growth is allowed.
  5. Compare and save. Review the setup and choose Validate and Save; choose a new .fwmg.json filename. Setup validates, compares and saves the project in one workflow. Check totals and all four checks in Output. A budget violation is a valid comparison, not an input error.
  6. Use it again. Complete a real change and successful rebuild, then run Compare Builds or Repeat Last Comparison. The current files are read again; keep the baseline fixed. Use Open Project to resume later.

Tell us the last step that worked, the first blocker and whether a second comparison helped. Export Report for Sharing opens reduced JSON for your review and optional Save As. It excludes paths, section names and symbols. Do not send firmware/source by default.

Host computer and firmware target are separate

RequirementCurrent scope
VS Code hostWindows x64; macOS Apple Silicon or Intel, declared macOS 15+; VS Code 1.85+. Guided WSL input access runs on the Windows host.
Firmware artifactsA complete GNU ld MAP and matching ARM ELF32 little-endian linked executable (ET_EXEC), from each successful build. ARM, file format and supported memory placement are required together.
Memory layoutOne selected region covering all active Flash load ranges and one selected region covering all active RAM run ranges; unchanged layout between baseline and current. Multiple named regions or aliases alone do not establish multiple active banks.
Excluded layoutsMultiple active banks that cannot fit the selected Flash/RAM pair; overlays or overlapping allocated ranges; dynamic linking, TLS, relocatable objects, unsupported/compressed allocated sections, and missing ELF section/program tables.
Other exclusionsNative Linux host, Remote-SSH, Dev Containers, Codespaces/browser execution, IAR/Keil or other unvalidated linker formats; runtime heap/stack peaks and object/library attribution.

The firmware operating system, board brand or compiler name alone does not establish compatibility. FreeRTOS, Zephyr, Pico, VxWorks and RISC-V are not covered by a blanket support claim. New combinations require their own artifact validation.

Accounting counts allocated output-section bytes. Initialized RAM also occupies Flash for its load image. Linker capacity and user budgets are separate quantities. Limits: 32 MiB per MAP, 64 MiB per ELF and 1 MiB per project JSON.
